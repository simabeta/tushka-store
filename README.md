# توشکا 🐰 — فروشگاه اینترنتی عروسک‌های پارچه‌ای

اپلیکیشن کامل و آماده production فروشگاه **توشکا** (عروسک‌های پارچه‌ای با عشق) با
**React 19 + TypeScript**، رابط کاربری کاملاً **فارسی و راست‌به‌چپ**، بک‌اند
**Supabase** (PostgreSQL + Auth + Storage + Edge Functions) و طراحی موبایل‌اول
الهام‌گرفته از هویت بصری صورتی برند.

| بخش | توضیح |
|---|---|
| ویندوز فروشگاه | صفحه اصلی، دسته‌بندی‌ها، صفحه محصول، جستجو، علاقه‌مندی‌ها |
| خرید | سبد خرید، تسویه حساب، ثبت سفارش با اعتبارسنجی سمت سرور |
| حساب کاربری | ثبت‌نام، ورود (ایمیل یا نام کاربری)، بازیابی گذرواژه، نشانی‌ها، سفارش‌ها |
| پنل مدیریت | داشبورد با نمودار فروش، مدیریت محصول/دسته/سفارش/مشتری، محتوا و تنظیمات |
| امنیت | RLS روی همه جداول، توابع امن، Storage Policies، بدون کلید محرمانه در مرورگر |

## 🗂 ساختار پروژه

```
├── src/
│   ├── app/                    # پوسته Next.js سندباکس (layout + globals.css)
│   ├── tushka/                 # ⭐ کل اپلیکیشن — مستقل از فریم‌ورک
│   │   ├── App.tsx             # روت‌های SPA (hash-router) + Splash
│   │   ├── lib/                # انواع، ابزارها، روتر، استورها
│   │   │   ├── api.ts          # لایه یکپارچه API (دمو ↔ Supabase)
│   │   │   ├── real-backend.ts # پیاده‌سازی واقعی Supabase
│   │   │   ├── demo/           # بک‌اند نمایشی درون‌مرورگری
│   │   │   └── supabase.ts     # ساخت کلاینت Supabase
│   │   ├── components/         # هدر، ناوبری، فوتر، کارت محصول، UI کیت
│   │   └── pages/              # صفحات فروشگاه + pages/admin (پنل)
│   └── public/                 # تصاویر برند، فونت Vazirmatn، favicon
├── supabase/
│   ├── migrations/             # ⭐ مایگریشن‌های SQL (اسکیما، RLS، توابع، سید)
│   ├── functions/              # ⭐ Edge Functions (سفارش، پرداخت، نقش)
│   └── admin-setup.sql.example # ساخت اولین مدیر
├── vite-template/              # ⭐ قالب آماده بیلد استاتیک Vite
├── docs/                       # چک‌لیست امنیت، استقرار، درگاه پرداخت
└── .env.example                # نمونه متغیرهای محیطی
```

> **معماری SPA و روتر هش‌محور:** کل رابط کاربری یک Single Page Application است و
> مسیرها با `#/` مدیریت می‌شوند (مثلاً `#/product/pink-bunny`). نتیجه: بیلد
> نهایی **کاملاً استاتیک** است و روی هر هاستی بدون rewrite کار می‌کند. کد
> `src/tushka` هیچ وابستگی به Next.js ندارد و با قالب `vite-template` به یک
> پروژه Vite استاندارد تبدیل می‌شود (راهنما: `vite-template/README.md`).

## 🚀 راه‌اندازی سریع (اتصال به Supabase)

### گام ۱ — ساخت پروژه Supabase
1. در [supabase.com](https://supabase.com) یک پروژه بسازید.
2. از **Project Settings → API** دو مقدار را بردارید:
   - `Project URL`
   - کلید عمومی (`anon` / `Publishable key`)

### گام ۲ — اجرای مایگریشن‌ها
به **SQL Editor** بروید و فایل‌ها را **به ترتیب** اجرا کنید:

| ترتیب | فایل | محتوا |
|---|---|---|
| ۱ | `supabase/migrations/0001_schema.sql` | جداول، ایندکس‌ها، تریگرها |
| ۲ | `supabase/migrations/0002_rls.sql` | RLS و سیاست‌های دسترسی |
| ۳ | `supabase/migrations/0003_functions.sql` | توابع امن (ثبت سفارش و…) |
| ۴ | `supabase/migrations/0004_storage.sql` | باکت‌ها و سیاست‌های Storage |
| ۵ | `supabase/migrations/0005_seed.sql` | داده نمونه (دسته‌بندی، محصول، بنر) |

### گام ۳ — ساخت حساب مدیر
طبق فایل `supabase/admin-setup.sql.example`:
1. **Authentication → Users → Add user**؛ ایمیل و یک گذرواژه **قوی و یکتا** بدهید و Auto Confirm را فعال کنید.
2. سپس در SQL Editor بخش ۲ آن فایل را اجرا کنید تا `username = admin` و نقش `admin` تخصیص یابد.
3. حالا در `/admin` با **نام کاربری `admin`** یا همان ایمیل وارد شوید.

> هیچ مسیر ثبت‌نام عمودی مدیر وجود ندارد؛ نقش admin فقط با این فرایند
> دست‌ساز و محافظت‌شده ساخته می‌شود.

### گام ۴ — پیکربندی احراز هویت
در **Authentication → URL Configuration**:
- **Site URL:** آدرس سایت (مثلاً `https://tushka.ir`)
- **Redirect URLs:** همان آدرس + `https://tushka.ir/#/auth` و `https://tushka.ir/#/reset-password`

**بازیابی گذرواژه:** اگر SMTP اختصاصی تنظیم نکرده باشید، Supabase از SMTP
داخلی خود (با محدودیت نرخ ارسال) استفاده می‌کند. برای production به
**Authentication → SMTP Settings** یک SMTP واقعی وصل کنید. تا زمانی که ایمیل
تنظیم نشده، ویژگی «ارسال لینک بازیابی/تأیید ایمیل» واقعاً کار نمی‌کند — اپ
هم همین را صادقانه به کاربر اعلام می‌کند.

### گام ۵ — متغیرهای محیطی و اجرا
```bash
cp .env.example .env.local
# مقادیر را وارد کنید:
#   NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
#   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=...
npm install && npm run dev        # نسخه Next سندباکس
```

برای **بیلد استاتیک Vite** (توصیه‌شده برای deployment): راهنمای کامل در
[`vite-template/README.md`](vite-template/README.md) — خروجی `dist/` روی
Vercel/Netlify/Cloudflare Pages یا هاست استاتیک قرار می‌گیرد.

## 🧪 حالت نمایشی (بدون Supabase)

اگر متغیرهای محیطی تنظیم نشده باشند، اپ در «حالت نمایشی» بالا می‌آید:
- همه داده‌ها فقط در **مرورگر شما** (localStorage) نگه‌داری می‌شوند؛
- بالای صفحه بنر شفاف «حالت نمایشی فعال است» دیده می‌شود؛
- حساب مدیر نمایشی: نام کاربری `admin` / گذرواژه `tushka-admin`؛
- حساب مشتری نمایشی: `sara@example.com` / `123456`؛
- قوانین اعتبارسنجی (قیمت، موجودی، انتقال وضعیت) دقیقاً مثل بک‌اند واقعی
  پیاده‌سازی شده تا رفتار محصول قابل پیش‌بینی باشد.

**هیچ داده واقعی یا حساسی در این حالت جایی ارسال نمی‌شود.**

## 🔐 مدل امنیتی (خلاصه)

| تهدید | پاسخ |
|---|---|
| دسترسی کاربر به داده دیگران | RLS روی **همه** جداول + سیاست‌های `auth.uid()` |
| دستکاری قیمت/تخفیف از مرورگر | قیمت فقط در تابع `place_order` از جدول `products` خوانده می‌شود |
| رقابت (race) در موجودی | `SELECT ... FOR UPDATE` روی ردیف‌های محصول داخل تراکنش |
| اضافه‌کردن خودش به‌عنوان admin | جدول `user_roles` بدون سیاست نوشتن؛ فقط توابع امن / service-role |
| آپلود فایل مخرب | محدودیت MIME + حجم در باکت + پاک‌سازی نام فایل |
| افشای service-role key | فقط در Edge Function Secrets؛ هرگز در باندل فرانت‌اند نیست |
| سوءاستفاده از SECURITY DEFINER | `set search_path = public` + مجوز دقیق execute |

جزئیات و چک‌لیست تست نفوذ دستی: [`docs/SECURITY-CHECKLIST.md`](docs/SECURITY-CHECKLIST.md)

## 🧾 وضعیت‌های سفارش و انتقال‌های مجاز

`pending_payment (در انتظار پرداخت) → paid (پرداخت‌شده) → processing (در حال آماده‌سازی) → shipped (ارسال‌شده) → delivered (تحویل‌شده)`

هر وضعیت با رعایت قوانین زیر قابل `cancelled (لغوشده)` می‌شود:
- مشتری: فقط در `pending_payment` (تابع `cancel_my_order` + بازگشت موجودی)
- مدیر: تا قبل از `delivered` (تابع `admin_update_order` + ثبت لاگ)

در پرداخت درگاهی، `paid` فقط پس از **verify سمت سرور** (Edge Function
`process-payment-callback`) ثبت می‌شود؛ پاسخ مرورگر هرگز ملاک نیست.

لایه پرداخت کامل طراحی شده (`payments`، وضعیت‌ها، رکورد authority/ref_id) و
نمونه یکپارچه‌سازی **زرین‌پال** با Edge Function نوشته شده است. راهنمای گام‌به‌گام:
[`docs/PAYMENT-GATEWAY.md`](docs/PAYMENT-GATEWAY.md)
تا زمان پیکربندی درگاه، سفارش‌ها با روش «پرداخت در محل» و وضعیت «در انتظار
پرداخت» ثبت می‌شوند.
