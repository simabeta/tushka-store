# 🔐 چک‌لیست تست امنیت — فروشگاه توشکا

این چک‌لیست را **پس از اتصال به پروژه واقعی Supabase** و قبل از انتشار اجرا کنید.
هر مورد را با هر سه نقش بررسی کنید: **بازدیدکننده ناشناس**، **مشتری عادی**، **مدیر**.

## ۱) احراز هویت
- [ ] ثبت‌نام با ایمیل جدید → پروفایل + سبد خرید + نقش customer خودکار ساخته می‌شود (تریگر `handle_new_user`).
- [ ] ورود با ایمیل و با نام کاربری (تابع `lookup_login_email`) هر دو کار می‌کند.
- [ ] گذرواژه اشتباه → پیام فارسی «ایمیل یا گذرواژه اشتباه است» بدون لو دادن وجود حساب.
- [ ] بازیابی گذرواژه: ایمیل می‌رسد (SMTP تنظیم‌شده) و لینک به `/#/reset-password` برمی‌گردد.
- [ ] خروج → توکن پاک می‌شود و صفحات محافظت‌شده ریدایرکت می‌شوند.
- [ ] حساب مسدودشده نمی‌تواند سفارش ثبت کند (`place_order` خطای blocked) و ورود برایش بسته است.

## ۲) Row Level Security (با SQL Editor تحت نقش anon/authenticated تست کنید)
- [ ] ناشناس: `select * from products` → فقط منتشرشده‌های فعال.
- [ ] ناشناس: `select * from orders / profiles / payments / admin_activity_logs` → **خالی**.
- [ ] مشتری: فقط سفارش‌ها، نشانی‌ها، سبد و علاقه‌مندی‌های خودش را می‌بیند.
- [ ] مشتری: `update profiles set is_blocked=true where id=own` → انجام نمی‌شود (فقط ستون‌های مجاز).
- [ ] مشتری: `insert into user_roles ... 'admin'` → **خطا** (هیچ سیاست insert وجود ندارد).
- [ ] مشتری: `update products set price=1` → **صفر ردیف**.
- [ ] مشتری: `insert into orders ...` → **خطا** (ثبت فقط با `place_order`).
- [ ] مدیر: فهرست مشتریان، همه سفارش‌ها و لاگ‌ها را می‌بیند.

## ۳) سفارش و موجودی
- [ ] تغییر قیمت محصول در مرورگر (DevTools → patch پاسخ) اثری روی مبلغ نهایی ندارد.
- [ ] ثبت هم‌زمان دو سفارش برای آخرین موجودی → فقط یکی موفق (قفل `FOR UPDATE`).
- [ ] سبد با تعداد بیشتر از موجودی → در سمت سرور رد می‌شود.
- [ ] لغو سفارش توسط مشتری → موجودی برمی‌گردد؛ لغو سفارش ارسال‌شده ممکن نیست.
- [ ] شماره سفارش یکتاست (`TSK-` + سکوئنس).

## ۴) پنل مدیریت
- [ ] `/admin` با حساب مشتری → پیام «دسترسی غیرمجاز».
- [ ] `/admin` بدون ورود → صفحه ورود اختصاصی.
- [ ] تغییر وضعیت‌های غیرمجاز (مثلاً delivered → processing) توسط API رد می‌شود.
- [ ] همه اقدامات مدیریتی در `admin_activity_logs` ثبت می‌شود.

## ۵) Storage
- [ ] آپلود با حساب مشتری/nاشناس → **خطای مجوز**.
- [ ] آپلود فایل غیرتصویری (مثلاً .html) → رد می‌شود (محدودیت MIME باکت).
- [ ] فایل بالای ۴ مگابایت → رد می‌شود.
- [ ] URL عمومی تصاویر بارگذاری‌شده در صفحه محصول نمایش داده می‌شود.

## ۶) وب اپلیکیشن
- [ ] هیچ کلید service-role در باندل نیست: `grep -r "service_role" dist/` خالی باشد.
- [ ] هدرهای امنیتی هاست تنظیم شده (X-Frame-Options، X-Content-Type-Options، Referrer-Policy).
- [ ] ورودی‌های فرم سمت سرور هم اعتبارسنجی می‌شوند (نشانگر تابع‌ها در SQL).
- [ ] پیام‌های خطا فارسی و بدون جزئیات فنی حساس‌اند.
- [ ] نرخ تلاش ورود توسط Supabase محدود شده (rate limit داخلی auth)؛ در صورت نیاز WAF اضافه کنید.

## ۷) ریسک‌های باقی‌مانده / محدودیت‌های شناخته‌شده
- محدودسازی نرخ پیشرفته (IP-based) به زیرساخت لایه‌های جلویی وابسته است.
- «امتیاز» کاربر در پروفایل فعلاً نمایشی و محاسبه‌شده سمت کلاینت است (بدون اثر مالی).
- ثبت نظر توسط مشتری هنوز از رابط کاربری وجود ندارد (فقط نمایش/مدیریت)؛ در صورت نیاز جدول `reviews` آماده است.
